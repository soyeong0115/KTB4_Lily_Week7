## 1단계 — 공통 인프라 (api/client.js, AuthContext, useModal)

| 항목 | 내용 |
|---|---|
| 작업 | `api/client.js`(request 함수 포팅), `AuthContext`/`useAuth`(accessToken state, login/logout), `ModalContext`/`useModal`/`Modal`(Promise 기반 confirm/alert, 로그인 필요 모달) 구현, `App.jsx`에 두 Provider 연결 |
| AI 제안 요약 | 설계 문서 2-5에 `useModal` 관련 state/함수/의존관계 초안 제시 후 검토받음. 구현은 "퀘스트" 방식 — 작은 과제로 쪼개서 순서대로 제시하고, 코드는 대부분 직접 작성. `api/client.js`는 리액트 문법이 필요 없는 순수 포팅이라 그대로 옮김. `Modal.jsx`의 JSX 마크업(기존 vanilla HTML 이식 부분)만 AI가 작성 |
| 검토 포인트 | 퀘스트마다 직접 작성한 코드를 AI가 리뷰 — `useState`/`useRef` 오용, Hooks 규칙 위반(`useNavigate`를 중첩 함수 안에서 호출), `setState`에 함수 직접 대입, Promise `resolve` 관련 실수 등 여러 차례 지적받고 수정. `npm run build`로 최종 빌드 확인 |
| 채택/수정 여부 | 설계 방향은 유지, 구현 코드는 직접 작성 — AI 제안을 그대로 받은 게 아니라 퀘스트마다 직접 코드를 치고, 버그를 리뷰받아 수정하며 완성 |
| 소요 시간 | 1시간 30분 — 세 컴포넌트 중 가장 오래 걸림. Promise/resolve 개념 자체를 처음 다뤄서 개념 질문이 많았고, `useModal`의 `showLoginRequireModal` 부분에서 버그 수정이 여러 차례 반복됨 |

**왜 이렇게 했는지 / 내 생각**
- 퀘스트 방식으로 직접 코드를 치면서 진행하니, 내가 정확히 어느 부분을 모르는지가 스스로 드러났다. 처음엔 "뭐부터 해야 할지" 막막했는데, 작게 쪼개진 과제를 하나씩 따라가다 보니 AI가 코드를 다 짜주는 것보다 오히려 길잡이를 받으며 직접 걸어가는 느낌이었다.
- `resolve`/`resolveRef` 개념은 이제 설명할 수 있다: `showConfirm`을 `await`으로 쓰고 싶어서 Promise로 감쌌고, Promise를 쓰려면 `resolve`가 필요하다. 근데 `resolve`를 실제로 호출해야 하는 시점(버튼 클릭)이 그걸 만든 시점(모달 오픈)과 다르고 함수도 다르기 때문에, 나중에 꺼내 쓸 수 있도록 `resolveRef`에 저장해두는 것이다.
- 시간이 없다고 하면서도 디테일 설계를 먼저 하고 구현으로 들어간 건 맞는 판단이었다고 생각한다. 구현부터 갔으면 일단 기능은 돌아가니까 이해를 대충 넘기고 지나갔을 것 같고, 그러면 내가 뭘 모르는지도 모른 채 넘어갔을 것 같다. 지금 방식으로 하니 어떤 부분에서 실수하는지도 알 수 있었다.

## 2단계 — 공통 컴포넌트 (SidebarTag, PrimaryButton, Header, AuthMenu)

| 항목 | 내용 |
|---|---|
| 작업 | `SidebarTag`, `PrimaryButton`(단순 표시용 컴포넌트), `Header`(로고+AuthMenu), `AuthMenu`(로그인 여부에 따라 로그인/회원가입 링크 또는 로그아웃 버튼 분기, `useAuth` 첫 소비) 구현. `Modal`은 1단계에서 이미 완료 |
| AI 제안 요약 | `SidebarTag`/`PrimaryButton`은 state가 없는 단순 컴포넌트라 설계 문서에 별도 상세 설계 없이 바로 퀘스트 진행. `AuthMenu`만 구현 후 설계 문서 2-5에 의존관계 간단히 추가(useAuth 첫 소비 사례라 기록해둘 가치 있다고 판단). 코드는 전부 직접 작성 |
| 검토 포인트 | JSX 문법 실수(`class` → `className` 안 바꿈, 컴포넌트가 형제 요소 2개를 그대로 반환하려 함) 다수 리뷰. `useAuth()` 호출 안 하고 변수처럼 씀, 배열 구조분해로 착각(객체인데) 등 지적받고 수정. `npm run build`로 확인 |
| 채택/수정 여부 | AuthMenu는 범위를 간단 버전(로그인 상태 텍스트/링크만)으로 축소 — 프로필 사진/닉네임 표시는 이후 단계로 미룸 |
| 소요 시간 | 20분 — `SidebarTag`/`PrimaryButton`은 단순 JSX 문법 실수 위주라 금방 끝났고, `AuthMenu`도 `useAuth` 사용법 실수 한두 번 정도로 1단계보다 수월했음 |

**왜 이렇게 했는지 / 내 생각**
- `AuthMenu` 범위를 간단 버전으로 줄인 이유: 프로필 사진/닉네임 표시는 API 연결이 필요한데, 이건 다른 단계(마이페이지/프로필 관련)의 일이다. 지금 단계에서 무리하게 다 넣기보다, 나중에 그 기능을 구현한 다음에 연결하는 게 더 실무적이고 자연스러운 순서라고 생각했다.
- `SidebarTag`/`PrimaryButton`처럼 단순한 컴포넌트는 설계 문서 없이 바로 구현했는데, 직접 해보니 왜 그래도 되는지 알겠다. 의존성이 없고 props만 받아서 그리는 컴포넌트는 애초에 설계할 state/useEffect/의존관계 자체가 없어서, 문서화할 대상이 없는 거였다.

## 3단계 — 인증 페이지 (ProtectedRoute, LoginPage, SignupPage)

| 항목 | 내용 |
|---|---|
| 작업 | `ProtectedRoute`(라우트 가드), `LoginPage`(이메일/비밀번호 검증 + 로그인), `SignupPage`(4개 필드 검증 + 프로필 이미지 업로드 + 회원가입) 구현 |
| AI 제안 요약 | 마크업(JSX 뼈대)은 AI가 이식, 검증/제출 로직은 퀘스트로 직접 작성. `LoginPage`에서 익힌 검증 패턴(값 state + 에러/유효 state 쌍 + onBlur 핸들러)을 `SignupPage`에서 반복 필드에 그대로 확장 적용 — 반복되는 건 빠르게, 이미지 업로드처럼 새로운 개념은 다시 퀘스트로 잘게 쪼개서 진행 |
| 검토 포인트 | `useState` 미호출/구조분해 누락, `setXxx = 값`처럼 함수 대신 대입, `Navigate`(컴포넌트)와 `navigate`(함수) 혼동, 서버로 보내는 필드명 불일치(`profileImageUrl` → `profileImage`), catch 블록에 `catch` 자체가 빠져 문법 에러 등 다수 리뷰. 특히 바닐라 JS 파일(`js/modal.js`)을 실수로 직접 import한 것을 발견해 `useModal` 훅으로 교체 — React 인프라를 우회하지 않도록 확인하는 게 중요했음 |
| 채택/수정 여부 | 설계 문서 2-5 상세 설계를 구현 전이 아니라 구현 **후**에 채워 넣음(순서를 놓침) — 그래도 이미 이해한 내용을 정리하는 방식으로 사후 작성. `Header`에 있던 뒤로가기 버튼은 이번 단계 범위에서 생략 |
| 소요 시간 | 1시간 |

**왜 이렇게 했는지 / 내 생각**
- 반복되는 부분(이메일/비밀번호 검증)이라고 해서 실수가 없었던 건 아니다. 대신 스스로 빠르게 진행하면서도 확실하게 알고 넘어가는 느낌이었다. 그리고 진행하다가 `LoginPage`와 `SignupPage`의 이메일/비밀번호 검증 로직이 거의 동일한 코드라는 걸 알아챘고, 이걸 재사용할 수 있는 방법은 없을까 하는 의문이 들었다 — 나중에 커스텀 훅으로 뽑아내는 리팩토링을 고민해볼 만한 지점이다.
- `js/modal.js`를 실수로 직접 import한 건 지적받기 전에 스스로 알아챘다 — 빌드해서 직접 동작을 확인하다가 이상해서 원인을 찾아보니 발견했다. 이 경험으로 명확해진 건, 바닐라 JS 파일을 직접 가져다 쓰면 그 모달은 `ModalProvider`가 관리하는 `modalState`/`resolveRef`와 완전히 분리된 별개의 시스템으로 동작한다는 점이다. 화면엔 뭔가 뜨더라도 앱 전체가 공유하는 하나의 모달 상태 밖에서 따로 노는 것이라, React로 마이그레이션한 의미 자체가 없어지는 셈이다.
- 설계 문서 2-5를 구현 후에 채운 건 이번 한 번이고, 다음 단계부터는 당연히 다시 설계를 먼저 정리하고 구현으로 들어갈 계획이다. 이번엔 마크업 이식 분량이 커서 순서가 흐트러졌을 뿐, 원칙 자체를 바꾼 건 아니다.

## 4단계 — 게시글 목록 (useInfiniteScroll, PostCard, PostList, PostSidebar, PostsPage)

| 항목 | 내용 |
|---|---|
| 작업 | `useInfiniteScroll`(커스텀 훅), `PostCard`(순수 표시), `PostList`(fetch + 무한 스크롤), `PostSidebar`(Info/글쓰기/Contributors), `PostsPage`(조립 + Contributors 상태 끌어올리기) 구현. 백엔드 CORS 설정에 React 개발 서버(5173) 추가, 게시글 없음 빈 상태 UI 추가 |
| AI 제안 요약 | 설계 문서 2-5에 5개 컴포넌트 상세 설계(state/useEffect/의존관계, 특히 "상태 끌어올리기") 먼저 작성 후 검토받고 구현. `useInfiniteScroll`은 처음엔 단순한 callback 방식으로 설계했다가, 이전에 다른 프로젝트에서 썼던 ref + `useCallback` 기반 패턴이 더 낫다는 판단하에 설계와 구현을 다시 고침. `PostCard`/`PostSidebar`는 state 없는 컴포넌트라 AI가 마크업 작성, 나머지는 퀘스트로 직접 구현 |
| 검토 포인트 | `useRef`/`useState` 혼동, `Set`에 배열 메서드(`.includes`) 사용, ref에 직접 값 재할당(사물함 자체를 바꿔치기), `.map()`에서 `return` 누락 등 반복 지적. 실제 브라우저로 확인하던 중 CORS 에러를 직접 발견해서, 원인이 프론트 코드가 아니라 백엔드 CORS 허용 목록 문제라는 걸 파악하고 직접 수정. 게시글 0개 상태에서 "빈 상태" UI가 없다는 것도 실사용 흐름에서 직접 발견 후 개선 요청 |
| 채택/수정 여부 | `useInfiniteScroll`은 설계를 구현 직전에 한 번 더 개선(ref 기반으로). 게시글 없음 빈 상태는 원래 설계에 없던 항목인데, 실사용 흐름에서 필요성을 발견해 추가 구현 — 아이콘/버튼/영역 크기/폰트까지 여러 차례 시각적으로 다듬음 |
| 소요 시간 | 4시간 30분 |

**왜 이렇게 했는지 / 내 생각**
- `useInfiniteScroll`을 더 나은 패턴으로 바꾸자고 먼저 제안할 수 있었던 건, 이전 단계들에서 내가 직접 지적하고 질문하며 이해를 쌓아왔기 때문이라고 생각한다. `observerRef`로 이름 짓고 싶었을 때 "이게 왜 헷갈리는 이름인지"를 짚었던 것, `targetRef`를 왜 반환해야 하는지 스스로 질문해서 ref와 실제 DOM 요소가 연결되는 원리를 이해한 것, `useEffect`의 의존성 배열을 매번 "이게 왜 필요해?"라고 캐물었던 것 — 이런 과정들이 쌓여서, 이번에 `useInfiniteScroll` 코드를 다시 보는 순간 "이 콜백이 렌더링마다 새로 만들어지면 비효율적이겠다"는 게 눈에 들어왔다. 그래서 예전에 다른 프로젝트에서 썼던 ref + `useCallback` 패턴을 먼저 꺼내서 "이렇게 바꿔도 되지 않냐"고 물어봤고, 그걸 이 프로젝트 스타일에 맞게 다시 조정해서 적용했다.
- CORS 에러는 이번에 자주 맞닥뜨렸던 문제이기도 하고, 디버그 로그를 직접 붙여서 확인하다 보니 원인이 프론트 코드가 아니라는 걸 판단할 수 있었다.
- 설계 문서에 없던 "게시글 없음" 빈 상태를 실사용 중에 발견하고 추가한 경험은, "설계 먼저"라는 원칙에 대한 확신을 오히려 더 굳혀줬다. 설계를 먼저 해야 뭘 해야 할지 머릿속에 그려지고, 그래야 개발/구현 자체에 집중할 수 있다. 그 위에서 실사용 확인을 통해 부족한 부분을 발견하고, 그걸 추가로 구현해나가는 순서가 맞는 방향이라고 생각한다.
- 4단계는 무한 스크롤이 들어가고 의존성도 많아서 이전 단계들보다 진행 속도는 확실히 느려졌다. 근데 자잘한 실수는 오히려 줄었다 — 반복해서 겪어본 패턴(state/ref 구분, 함수 호출 vs 대입 등)에서는 실수가 줄고, 새로운 개념에서만 막히는 식으로 바뀐 것 같다.

## 5단계 — 게시글 상세 (PostDetailPage, CommentForm, CommentList, CommentItem)

| 항목 | 내용 |
|---|---|
| 작업 | `CommentItem`/`CommentList`(AI가 마크업+로직 작성, 리뷰하며 이해), `CommentForm`(등록/수정, 퀘스트), `PostDetailPage`(본문+좋아요+조회수+댓글 CRUD+소유자별 수정/삭제, 퀘스트) 구현. `useModal` 훅의 오래된 버그(이름 불일치, `isAuthError` 누락) 발견 및 수정 |
| AI 제안 요약 | 설계 문서 2-5에 조회수 처리 방식(`shouldCountViewRef`)과 소유자(`myPost`) 상태를 구체적으로 먼저 정리(피드백에서 짚었던 두 가지). `CommentForm`은 props(`editingComment`) 동기화에 `useEffect`를 처음 도입, `PostDetailPage`는 마크업은 AI가 이식하고 조회수/좋아요/삭제 로직은 퀘스트로 진행 |
| 검토 포인트 | 삼항 연산자 값에 대입식을 넣는 실수, `async` 누락, `+`/템플릿 리터럴 혼동 등 리뷰. AI가 playwright로 실제 브라우저 테스트를 하다가 존재하지 않는 게시글(404) 경로에서 `showAlertModal is not a function` 크래시를 발견 — `useModal.js`가 `ModalContext`의 `showConfirm`/`showAlert`를 이름 그대로 넘기고 있었고, `isAuthError`는 애초에 구현조차 안 되어 있었음 |
| 채택/수정 여부 | 4개 파일(`SignupPage`, `CommentForm`, `CommentItem`, `PostDetailPage`)을 각각 고치는 대신, 근본 원인인 `useModal.js` 한 곳만 고쳐서 전부 정상화하는 방향으로 수정 — 사용하는 쪽 이름은 처음부터 맞았고 훅 자체가 틀렸던 것이라, 원인 지점을 고치는 게 맞다고 판단 |
| 소요 시간 | 2시간 |

**왜 이렇게 했는지 / 내 생각**
- 조회수 처리 방식과 `myPost` 소유자 상태를 구현 전에 미리 상세하게 정리해둔 게 완전히 도움이 됐다. 코드를 짜기 전에 "이 값은 ref로, 저 값은 post state 안에" 같은 결정이 이미 끝나 있으니까, 막상 구현할 때는 그 결정을 그대로 옮기기만 하면 됐다. 만약 설계 없이 바로 짰다면, 코드를 치면서 동시에 "이걸 어떻게 관리해야 하지"까지 그때그때 고민해야 했을 텐데, 그 두 가지를 분리해둔 덕분에 구현 자체에만 집중할 수 있었다.
- 마이그레이션을 하면서도 실제로 자세하게 동작을 확인하는 테스트가 중요하다는 걸 다시 느꼈다. 빌드가 성공한다고 해서 실제로 다 동작하는 건 아니라는 걸 `useModal` 버그를 통해 직접 느낄 수 있었다.
- `CommentForm`의 `useEffect`(props를 state에 동기화)가 `useInfiniteScroll`의 `useEffect`(브라우저 API 연결)보다 훨씬 단순하게 느껴졌다. 전자는 그냥 "이 값이 바뀌면 저 값도 맞춰라"는 한 줄짜리 동기화라 cleanup도 필요 없는데, 후자는 리액트 바깥의 진짜 API(`IntersectionObserver`)를 다루다 보니 만들고 없애는 과정(cleanup)까지 신경 써야 했다. 이 둘을 나란히 써보니 `useEffect`가 하는 일 자체는 "뭔가 바뀌면 반응한다"로 같아도, 안에서 다루는 대상이 리액트 내부 값이냐 리액트 바깥의 것(구독, 타이머, 브라우저 API)이냐에 따라 복잡도가 완전히 달라진다는 걸 확실히 이해했다. 각각 언제 써야 하는지도 감이 잡혔다.
- 5단계까지 오면서, 내가 어느 부분을 모르고 어디서 실수하는지 확실하게 알 수 있게 됐다. 반복되는 작업으로 시간이 소요되는 부분은 AI가 대신 해주고, 나는 직접 이해하고 공부해야 하는 부분에 시간을 쓰는 식으로 역할을 나눌 수 있었던 것 같다.

## 6단계 — 게시글 작성/수정 (PostForm, PostCreatePage, PostEditPage)

| 항목 | 내용 |
|---|---|
| 작업 | `js/post-create.js`/`js/post-edit.js` diff 기반으로 공용 `PostForm`(`mode` prop) 구현. `PostCreatePage`/`PostEditPage`는 `Header`+`PostForm` 조립 |
| AI 제안 요약 | 두 원본 파일을 비교해서 실제로 다른 부분 5가지(초기 fetch 유무/제출 API·메서드/이동 경로/헤딩 문구/버튼 라벨)만 뽑아 설계 문서에 정리 후 검토. `PostForm`의 마크업은 AI가 이식, state/이미지 업로드/`useEffect`/제출 로직은 퀘스트로 직접 구현. `PostCreatePage`/`PostEditPage` 조립은 직접 작성 |
| 검토 포인트 | `fileInputRef`를 실제 `<input>`에 연결 안 함, `useEffect` 콜백을 `async`로 만들려던 실수(리액트 규칙 위반) 등 리뷰. 제출 버튼 `onClick` 누락, `showAlertModal` `await` 누락 등도 지적 |
| 채택/수정 여부 | 빈 값 검증 실패 메시지는 원본에 모드별로 다르게 있어서 그대로 분기하자고 제안받았으나, 내용이 사실상 같고 표현만 다른 수준이라 굳이 분기할 필요 없다고 판단해 하나로 통일하는 쪽으로 의도적으로 다르게 결정 |
| 소요 시간 | 1시간 |

**왜 이렇게 했는지 / 내 생각**
- diff 기반 설계가 확실히 도움이 됐다. 그동안 "컴포넌트를 어떤 기준으로 뽑고, 어디서부터 어디까지를 공통점으로 봐서 재사용 가능한 컴포넌트로 만들어야 하는지"에 대한 고민과 의문이 있었는데, 이번에 두 파일을 실제로 비교해서 "이 정도까지만 다르구나"를 직접 확인해보니 감이 왔다. 모드별로 분기해서 하나의 컴포넌트로 합치니까 코드도 간결해지고, 나중에 봤을 때 이해/확인도 훨씬 쉬웠다.
- `useEffect`가 `async`가 될 수 없는 이유가 궁금해서 끝까지 물어봤다. 다음에 코드를 짤 때 헷갈리지 않고 바로 적용할 수 있을 것 같다.
- 원본을 그대로 포팅할지, 개선할지 판단하는 기준은 "AI가 제안하되, 내가 검토해서 이상한 부분은 적용 안 하고 개선이 필요한 부분은 내가 판단해서 바꾼다"는 쪽으로 정리됐다. 이번 검증 메시지 통일도 그 판단 기준을 적용한 사례다.
- 6단계까지 오면서 가장 크게 느낀 건 AI 의존도가 떨어졌다는 점이다. AI를 믿고 그대로 적용하지 않고 내 판단하에 결정하다 보니, 단순히 기존 바닐라 JS를 리액트로 그대로 옮기는 걸 넘어서 원본에서 미처 발견하지 못했던 빈틈을 내가 채워나가는 느낌이 들었다.
