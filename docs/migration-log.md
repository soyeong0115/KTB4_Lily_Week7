## 1단계 — 공통 인프라 (api/client.js, AuthContext, useModal)

| 항목 | 내용 |
|---|---|
| 작업 | `api/client.js`(request 함수 포팅), `AuthContext`/`useAuth`(accessToken state, login/logout), `ModalContext`/`useModal`/`Modal`(Promise 기반 confirm/alert, 로그인 필요 모달) 구현, `App.jsx`에 두 Provider 연결 |
| AI 제안 요약 | 설계 문서 2-5에 `useModal` 관련 state/함수/의존관계 초안 제시 후 검토받음. 구현은 "퀘스트" 방식 — 작은 과제로 쪼개서 순서대로 제시하고, 코드는 대부분 직접 작성. `api/client.js`는 리액트 문법이 필요 없는 순수 포팅이라 그대로 옮김. `Modal.jsx`의 JSX 마크업(기존 vanilla HTML 이식 부분)만 AI가 작성 |
| 검토 포인트 | 퀘스트마다 직접 작성한 코드를 AI가 리뷰 — `useState`/`useRef` 오용, Hooks 규칙 위반(`useNavigate`를 중첩 함수 안에서 호출), `setState`에 함수 직접 대입, Promise `resolve` 관련 실수 등 여러 차례 지적받고 수정. `npm run build`로 최종 빌드 확인 |
| 채택/수정 여부 | 설계 방향은 유지, 구현 코드는 직접 작성 — AI 제안을 그대로 받은 게 아니라 퀘스트마다 직접 코드를 치고, 버그를 리뷰받아 수정하며 완성 |
| 소요 시간 | 1시간 30분 — 세 컴포넌트 중 가장 오래 걸림. Promise/resolve 개념 자체를 처음 다뤄서 개념 질문이 많았고, `useModal`의 `showLoginRequireModal` 부분에서 버그 수정이 여러 차례 반복됨 |

**왜 이렇게 했는지 / 내 생각**
- 퀘스트 방식으로 직접 코드를 치면서 진행하니, 내가 정확히 어느 부분을 모르는지가 스스로 드러났다. 처음엔 "뭐부터 해야 할지" 막막했는데, 작게 쪼개진 과제를 하나씩 따라가다 보니 AI가 코드를 다 짜주는 것보다 오히려 길잡이를 받으며 직접 걸어가는 느낌이었다.
- `resolve`/`resolveRef` 개념은 이제 설명할 수 있다: `showConfirm`을 `await`으로 쓰고 싶어서 Promise로 감쌌고, Promise를 쓰려면 `resolve`가 필요하다. 근데 `resolve`를 실제로 호출해야 하는 시점(버튼 클릭)이 그걸 만든 시점(모달 오픈)과 다르고 함수도 다르기 때문에, 나중에 꺼내 쓸 수 있도록 `resolveRef`에 저장해두는 것이다.
- 시간이 없다고 하면서도 디테일 설계를 먼저 하고 구현으로 들어간 건 맞는 판단이었다고 생각한다. 구현부터 갔으면 일단 기능은 돌아가니까 이해를 대충 넘기고 지나갔을 것 같고, 그러면 내가 뭘 모르는지도 모른 채 넘어갔을 것 같다. 지금 방식으로 하니 어떤 부분에서 실수하는지도 알 수 있었다.

## 2단계 — 공통 컴포넌트 (SidebarTag, PrimaryButton, Header, AuthMenu)

| 항목 | 내용 |
|---|---|
| 작업 | `SidebarTag`, `PrimaryButton`(단순 표시용 컴포넌트), `Header`(로고+AuthMenu), `AuthMenu`(로그인 여부에 따라 로그인/회원가입 링크 또는 로그아웃 버튼 분기, `useAuth` 첫 소비) 구현. `Modal`은 1단계에서 이미 완료 |
| AI 제안 요약 | `SidebarTag`/`PrimaryButton`은 state가 없는 단순 컴포넌트라 설계 문서에 별도 상세 설계 없이 바로 퀘스트 진행. `AuthMenu`만 구현 후 설계 문서 2-5에 의존관계 간단히 추가(useAuth 첫 소비 사례라 기록해둘 가치 있다고 판단). 코드는 전부 직접 작성 |
| 검토 포인트 | JSX 문법 실수(`class` → `className` 안 바꿈, 컴포넌트가 형제 요소 2개를 그대로 반환하려 함) 다수 리뷰. `useAuth()` 호출 안 하고 변수처럼 씀, 배열 구조분해로 착각(객체인데) 등 지적받고 수정. `npm run build`로 확인 |
| 채택/수정 여부 | AuthMenu는 범위를 간단 버전(로그인 상태 텍스트/링크만)으로 축소 — 프로필 사진/닉네임 표시는 이후 단계로 미룸 |
| 소요 시간 | 20분 — `SidebarTag`/`PrimaryButton`은 단순 JSX 문법 실수 위주라 금방 끝났고, `AuthMenu`도 `useAuth` 사용법 실수 한두 번 정도로 1단계보다 수월했음 |

**왜 이렇게 했는지 / 내 생각**
- `AuthMenu` 범위를 간단 버전으로 줄인 이유: 프로필 사진/닉네임 표시는 API 연결이 필요한데, 이건 다른 단계(마이페이지/프로필 관련)의 일이다. 지금 단계에서 무리하게 다 넣기보다, 나중에 그 기능을 구현한 다음에 연결하는 게 더 실무적이고 자연스러운 순서라고 생각했다.
- `SidebarTag`/`PrimaryButton`처럼 단순한 컴포넌트는 설계 문서 없이 바로 구현했는데, 직접 해보니 왜 그래도 되는지 알겠다. 의존성이 없고 props만 받아서 그리는 컴포넌트는 애초에 설계할 state/useEffect/의존관계 자체가 없어서, 문서화할 대상이 없는 거였다.

## 3단계 — 인증 페이지 (ProtectedRoute, LoginPage, SignupPage)

| 항목 | 내용 |
|---|---|
| 작업 | `ProtectedRoute`(라우트 가드), `LoginPage`(이메일/비밀번호 검증 + 로그인), `SignupPage`(4개 필드 검증 + 프로필 이미지 업로드 + 회원가입) 구현 |
| AI 제안 요약 | 마크업(JSX 뼈대)은 AI가 이식, 검증/제출 로직은 퀘스트로 직접 작성. `LoginPage`에서 익힌 검증 패턴(값 state + 에러/유효 state 쌍 + onBlur 핸들러)을 `SignupPage`에서 반복 필드에 그대로 확장 적용 — 반복되는 건 빠르게, 이미지 업로드처럼 새로운 개념은 다시 퀘스트로 잘게 쪼개서 진행 |
| 검토 포인트 | `useState` 미호출/구조분해 누락, `setXxx = 값`처럼 함수 대신 대입, `Navigate`(컴포넌트)와 `navigate`(함수) 혼동, 서버로 보내는 필드명 불일치(`profileImageUrl` → `profileImage`), catch 블록에 `catch` 자체가 빠져 문법 에러 등 다수 리뷰. 특히 바닐라 JS 파일(`js/modal.js`)을 실수로 직접 import한 것을 발견해 `useModal` 훅으로 교체 — React 인프라를 우회하지 않도록 확인하는 게 중요했음 |
| 채택/수정 여부 | 설계 문서 2-5 상세 설계를 구현 전이 아니라 구현 **후**에 채워 넣음(순서를 놓침) — 그래도 이미 이해한 내용을 정리하는 방식으로 사후 작성. `Header`에 있던 뒤로가기 버튼은 이번 단계 범위에서 생략 |
| 소요 시간 | 1시간 |

**왜 이렇게 했는지 / 내 생각**
- 반복되는 부분(이메일/비밀번호 검증)이라고 해서 실수가 없었던 건 아니다. 대신 스스로 빠르게 진행하면서도 확실하게 알고 넘어가는 느낌이었다. 그리고 진행하다가 `LoginPage`와 `SignupPage`의 이메일/비밀번호 검증 로직이 거의 동일한 코드라는 걸 알아챘고, 이걸 재사용할 수 있는 방법은 없을까 하는 의문이 들었다 — 나중에 커스텀 훅으로 뽑아내는 리팩토링을 고민해볼 만한 지점이다.
- `js/modal.js`를 실수로 직접 import한 건 지적받기 전에 스스로 알아챘다 — 빌드해서 직접 동작을 확인하다가 이상해서 원인을 찾아보니 발견했다. 이 경험으로 명확해진 건, 바닐라 JS 파일을 직접 가져다 쓰면 그 모달은 `ModalProvider`가 관리하는 `modalState`/`resolveRef`와 완전히 분리된 별개의 시스템으로 동작한다는 점이다. 화면엔 뭔가 뜨더라도 앱 전체가 공유하는 하나의 모달 상태 밖에서 따로 노는 것이라, React로 마이그레이션한 의미 자체가 없어지는 셈이다.
- 설계 문서 2-5를 구현 후에 채운 건 이번 한 번이고, 다음 단계부터는 당연히 다시 설계를 먼저 정리하고 구현으로 들어갈 계획이다. 이번엔 마크업 이식 분량이 커서 순서가 흐트러졌을 뿐, 원칙 자체를 바꾼 건 아니다.
